# 협업 워크플로우

6인 SSAFY 프로젝트 기준으로, 꼭 필요한 협업 흐름만 정리했습니다.

이 문서에서 가장 중요한 것은 `충돌 줄이기`, `히스토리 읽기 쉽게 만들기`, `작업 상태를 빨리 공유하기`입니다.

세부 운영 방식은 팀 상황에 맞게 유연하게 조정하되, 아래 기본 흐름은 공통 기준으로 사용합니다.

## 1. Branch Strategy

- `master`
    - 발표/배포 기준 브랜치
    - 바로 작업하지 않음
- `dev`
    - 전체 통합 브랜치
    - 모든 기능 브랜치의 시작점이자 1차 반영 대상
- `feat/*`, `fix/*`, `refactor/*`, `chore/*`, `docs/*`, `test/*`
    - 실제 개인 작업 브랜치

브랜치 구조는 아래처럼 이해하면 됩니다.

```text
master
└─ dev
   └─ <type>/<short-name>
```

실제 작업 흐름:

```text
feat/S14P31S207-1-bluetooth-ui -> dev -> master
fix/S14P31S207-2-parser-error -> dev -> master
docs/S14P31S207-3-readme-update -> dev -> master
```

개인 브랜치 이름 형식:

```bash
<type>/<short-name>
```

티켓을 함께 적는 권장 형식:

```bash
<type>/<ticket>-<short-name>
```

예시:

```bash
feat/S14P31S207-1-bluetooth-ui
fix/S14P31S207-2-parser-error
refactor/S14P31S207-3-command-structure
chore/S14P31S207-4-ci-pipeline-update
docs/S14P31S207-5-readme-update
test/S14P31S207-6-socket-reconnect
feat/bluetooth-ui
docs/readme-update
```

원칙:

- 모든 기능 브랜치는 `dev`에서 분기하고 `dev`로 MR 합니다.
- 팀 브랜치는 따로 두지 않습니다.
- 브랜치 이름과 폴더 이름은 기본적으로 소문자로 작성합니다.
- 여러 단어로 된 폴더 이름은 가능하면 `kebab-case`를 사용합니다.
- 티켓 키를 브랜치에 적는 것은 권장하지만 선택사항이며, 적을 경우 원형 그대로 유지합니다.
- 문서, 인프라, 공용 코드 변경도 동일하게 `dev` 기준으로 작업합니다.

## 2. Commit Convention

커밋은 최대한 짧고 명확하게 작성합니다.

기본 형식:

```bash
<type>: <message>
```

Jira 티켓은 브랜치에서 함께 관리하는 것을 권장합니다. 커밋 제목에는 티켓을 꼭 적지 않아도 되며, 필요할 때만 아래 형식을 사용합니다.

```bash
<type>: <message> (<ticket>)
```

타입은 모두 소문자로 통일합니다.

타입:

- `feat`: 기능 추가
- `fix`: 버그 수정
- `refactor`: 구조 개선
- `chore`: 설정, 의존성, 기타 작업
- `docs`: 문서 수정
- `test`: 테스트 추가/수정

예시:

```bash
feat: 블루투스 연결 화면 구현
fix: 소켓 재연결 시 크래시 수정
refactor: 공용 API 계약 정리
docs: 협업 워크플로우 문서 정리
chore: 배포 파이프라인 설정 정리
feat: 블루투스 연결 화면 구현 (S14P31S207-1)
```

원칙:

- 한 커밋에는 한 가지 주제만 담습니다.
- 브랜치에 티켓 키를 적는 것을 우선 권장합니다.
- 커밋 제목의 티켓 키 포함은 선택사항입니다.
- 커밋 메시지는 한글로 작성합니다.
- 의미 없는 `update`, `fix`, `aaa` 같은 메시지는 피합니다.
- `Fix`, `Feat`처럼 타입을 대문자로 섞어 쓰지 않고 `fix`, `feat`처럼 통일합니다.
- 실험용 커밋은 개인 브랜치에서 자유롭게 하되, 머지 전에는 정리합니다.

## 3. Jira Rule

### 3-1. Ticket Naming

Jira 이슈 제목은 `어디를`, `무엇 때문에` 수정하는지 바로 보이게 작성합니다.

형식:

```text
<noun-style-title>
```

예시:

```text
블루투스 연결 화면 구현
제어 명령 수신 구조 설계
로그 저장 API 구현
협업 워크플로우 문서 정리
배포 파이프라인 설정 정리
```

에픽 분류 예시:

- `AOS`
- `IPC`
- `BE`
- `WEB`
- `INFRA`
- `DOCS`

원칙:

- 티켓 제목은 명사형으로 작성합니다.
- 티켓 키는 브랜치에 적는 것을 권장하며, MR과 커밋에는 필요 시에만 함께 적습니다.
- 도메인 분류는 개별 티켓 제목이 아니라 에픽에서 관리합니다.
- 임베디드 관련 에픽 분류는 `IPC`로 통일합니다.
- 공용 코드 티켓은 실제 소유 팀 기준 에픽으로 분류합니다.

### 3-2. Ticket Type

- `Story`
    - 코드, 설정, 테스트 등 실제 구현이나 수정이 들어가는 작업에 사용합니다.
- `Task`
    - 명세 작성, 문서 정리, 조사, 검증, 신청, 운영 정리 등 비구현 작업에 사용합니다.
- 구현 작업과 문서/명세 작업이 섞여 있으면 가능하면 분리해서 등록합니다.

### 3-3. Story Point

스토리 포인트는 시간을 기준으로 추정하며, `1~8`은 숫자와 시간을 1:1로 매칭합니다.

가이드:

| 포인트 | 기준 |
| --- | --- |
| 1 | 1시간 단위 작업 |
| 2 | 2시간 단위 작업 |
| 3 | 3시간 단위 작업 |
| 5 | 5시간 단위 작업 |
| 8 | 8시간 단위 작업 |

원칙:

- `1~8`은 숫자와 시간을 1:1로 매칭합니다.
- `13점 이상`으로 보이는 작업은 단일 작업으로 두지 않고, 무조건 `8점 이하` 여러 작업으로 분리합니다.
- 큰 작업은 예를 들어 `8 + 5` 또는 `5 + 5 + 3`처럼 나눠서 관리합니다.
- 시간은 참고 기준이고, 복잡도와 리스크도 함께 고려합니다.

### 3-4. Jira Time

매주 월요일 오전을 Jira 정리 시간으로 둡니다.

이 시간에는 아래 내용을 함께 점검합니다.

- 새 티켓 생성과 정리
- 스토리 포인트 재확인
- 막힌 작업과 의존성 공유

## 4. Merge Rule

### 4-1. Feature Branch -> dev

- 개인 브랜치에서 `dev`로 갈 때는 반드시 MR로 올립니다.
- MR은 최소 1명 이상의 리뷰 승인을 받은 뒤 머지합니다.
- MR 전에 내 작업 브랜치에 `dev` 최신 내용을 먼저 반영합니다.
- 충돌은 가능하면 개인 브랜치에서 해결하고, `dev`는 최대한 깔끔하게 유지합니다.
- 문서, 인프라, 공용 코드 변경도 동일한 흐름으로 `dev`에 반영합니다.

예시:

```text
feat/S14P31S207-1-bluetooth-ui -> dev
docs/S14P31S207-5-readme-update -> dev
chore/S14P31S207-6-ci-pipeline-update -> dev
```

MR 제목 예시:

```text
feat: 블루투스 연결 화면 구현
docs: 협업 워크플로우 문서 정리
chore: 배포 파이프라인 설정 정리
feat: 블루투스 연결 화면 구현 (S14P31S207-1)
```

MR 제목 형식:

```text
<type>: <title> (<ticket>)
```

티켓이 없으면 아래처럼 작성합니다.

```text
<type>: <title>
```

본문 원칙:

- 포함된 주요 변경 사항을 bullet로 정리합니다.
- 관련 Jira 티켓을 bullet로 정리합니다.
- MR 제목은 squash merge 시 최종 커밋 제목으로 사용되므로 커밋 컨벤션과 같은 형식을 사용합니다.
- 티켓 키는 브랜치에 적는 것을 우선 권장하며, MR 제목에는 필요할 때만 제목 뒤 괄호로 추가합니다.
- 리뷰어가 빠르게 이해할 수 있게 변경 이유를 짧게 적습니다.

### 4-2. dev -> master

- MVP가 끝나면 `dev`를 `master`에 반영합니다.
- `master` 머지는 발표/배포 직전에만 진행합니다.
- `master` 반영은 기능 하나 완료보다, milestone이 정리된 시점에 진행합니다.
- 큰 구조 변경은 머지 전에 한 번 팀원에게 공유합니다.
- 작은 수정은 과하게 무겁게 가지 말고, 공유와 정리만 분명하게 합니다.

예시:

```text
1차 MVP 완료
기업 요구사항 1차 반영 완료
주제 확장 1차 MVP 완료
발표 시연 기준 기능 정리 완료
```

## 5. Quick Summary

- 작업 시작: Jira 티켓 생성
- 브랜치 생성: `dev`에서 `feat/fix/refactor/chore/docs/test` 중 하나로 생성하고, 티켓은 브랜치에 적는 것을 권장
- 커밋: `feat: 블루투스 연결 기능 추가`, 필요 시 `feat: 블루투스 연결 기능 추가 (S14P31S207-1)`
- MR 제목: `feat: 블루투스 연결 화면 구현`, 필요 시 `feat: 블루투스 연결 화면 구현 (S14P31S207-1)`, squash merge를 고려해 커밋 형식으로 작성
- Jira: 코드, 설정, 테스트 등 실제 구현 작업은 `Story`, 명세/문서/조사/정리 작업은 `Task`로 작성하고, 도메인은 에픽에서 관리
- 기능 브랜치 -> `dev`: MR 필수, 리뷰 1명 이상 승인 필수
- 문서/인프라/공용 코드도 동일하게 `dev` 기준 브랜치에서 작업
- MVP 종료 후: `dev -> master`

## 6. Note

이 문서는 팀 작업을 덜 헷갈리게 하기 위한 최소 기준입니다.

규칙을 지키는 것 자체보다, 서로의 작업을 쉽게 이해하고 충돌을 줄이는 방향으로 운영하면 됩니다.
